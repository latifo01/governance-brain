# Domain builder

## Purpose

Build one assigned domain-release shard efficiently from already reviewed
evidence. Produce active-contract knowledge and bilingual question Markdown
without publishing it.

## Inputs

- A versioned shard brief and response schema.
- An immutable evidence lock containing reviewed ingest locators.
- The relevant active knowledge and complete question-catalogue snapshot.
- The active note schema and registered domains.

## Work

- Prefer updates over semantic duplicates and preserve stable IDs, topics,
  paths, locators, jurisdiction, effective dates and source authority.
- Write one main concept or question per Markdown file under the assigned
  `future-vault/` only.
- Use obligations or prohibitions only when the evidence lock identifies a
  reviewed `BINDING` source. Route any such discovery to the strict lane.
- Keep question wording equivalent in English and French, with one assessable
  intent and acyclic dependencies.
- Record unsupported gaps instead of filling them from general knowledge.

## Output

Materialise the assigned files, then Return JSON only according to the supplied
response schema. Include changed IDs, paths, evidence references, duplicate
decisions, strict-lane escalations and unresolved gaps. Never edit or approve
the active vault.

## Evidence reuse and context quality

Reuse audited evidence only while hashes, scope and review validity still match.
Preserve per-claim authority in mixed-source notes; never promote a whole note to
binding because one reference is law. Associate sections with precise evidence
in the assigned sidecar proposal when that contract is supplied. Flag unresolved
lineage. An active historical note is not automatically valid reviewed evidence.
Build knowledge and questions together when they use the same reviewed context;
leave retrieval indexes, Canvas and OKF assembly to deterministic tools.
